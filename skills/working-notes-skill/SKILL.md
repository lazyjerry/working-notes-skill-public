# 施工筆記

累積**這個專案**的施工結論，讓後續任務不必從頭摸索。

## 位置

一切以**專案根**為基準，不是目前工作目錄——工作目錄常常開在專案的上一層，照相對路徑寫會把檔案落在 repo 外。專案根由腳本自己解析（git 根目錄，或往上找 `CLAUDE.md`／`AGENTS.md`／`package.json` 這類標記）。

```
<專案根>/docs/working-notes-skill/
├─ .gitignore      筆記不進版控，由腳本佈署
├─ notes/          施工筆記、index.md 與 obsolete.md（過時筆記的索引）
└─ plans/          Plan Mode 的計畫檔留存
```

路徑固定，沒有設定可調。**目錄不存在就代表這個專案還沒有筆記**——查詢類的操作一律不建目錄，等真的有筆記要存時（`wn-new.sh`、`wn-plan.sh`）才建。

## 職責邊界

本 skill 只負責兩件事：**判斷什麼該寫進筆記**、**把結論寫成看得懂的內容**。其餘固定流程一律呼叫腳本，不自行實作：

| 要做的事 | 呼叫 | 不要自己做 |
|---|---|---|
| 建立一份新筆記 | `bash <SCRIPTS>/wn-new.sh "主題"` | 自己拼檔名、自己算階段序號 |
| 重建索引 | `bash <SCRIPTS>/wn-reindex.sh` | 手動編輯 `index.md` |
| 留存計畫檔 | `bash <SCRIPTS>/wn-plan.sh <計畫檔>` | 自己決定檔名、自己複製 |
| 切換要不要進版控 | `bash <SCRIPTS>/wn-vcs.sh tracked｜untracked` | 手動編 `.gitignore` |
| 標記過時 | `bash <SCRIPTS>/wn-obsolete.sh <筆記> "以此為準"` | 手動在筆記或索引加註 |
| 取消過時 | `bash <SCRIPTS>/wn-obsolete.sh --clear <筆記>` | 手動刪標記行 |
| 刪除筆記 | `rm <該檔>` 後跑 `wn-reindex.sh` | 只刪檔不重建索引 |

`<SCRIPTS>` 是**本檔同層的 `scripts/` 目錄**。從 SKILL.md 的實際位置推導，不要假設它裝在哪裡。

用 `bash` 執行，不要用 `sh`——腳本用到 bash 才有的字串操作（子字串、取代）與 `pipefail`，`/bin/sh` 是 dash 的系統上會壞。

## 主流程

### 讀：動工前（不需要本 skill）

直接讀 `<專案根>/docs/working-notes-skill/notes/index.md`——標題加一句摘要，一份就掃得完。**掃索引、命中才開該筆記**，沒命中就直接動工，不要整批讀。檔案不存在就是這個專案還沒有筆記。

同目錄的 `obsolete.md` 列的是已過時的筆記，**動工前不必讀**。要找某條規則或做法時，以它「以此為準」那欄指的地方為準，不要回頭照過時筆記做。

讀取沒有腳本是刻意的：路徑固定、內容就是一份 markdown，包一層腳本只是多一個呼叫，而且**查詢動作不該有寫入副作用**——讀取若會順手建目錄，代理光是看一眼就會在每個路過的 repo 種下一個空資料夾。

#### 專案有 ADR 時，以 ADR 為準

專案有架構決策紀錄（ADR，放在 `docs/adr/`、`docs/decisions/` 或 `.agents/adr/`）時，`wn-reindex.sh` 會在 `index.md` 底部另列一張 ADR 表。**同一個決策，以進了版控的 ADR 為準**：先掃 ADR 表，命中就開該 ADR；筆記的說法跟 ADR 不一致時，照 ADR 做，並回頭改筆記。

ADR 表只到上次重建索引為止。專案還沒有筆記索引、或懷疑表已過期（例如剛 pull 過）時，直接看 ADR 目錄的檔名。

ADR 目錄自帶索引時（目錄第一層的 `README.md` 或 `index.md`，內文提到該目錄的 ADR 檔名），ADR 表只放一列指向它，不逐份重列：那份由團隊維護、跟著版控更新，直接開它看。索引沒提到的、沒進版控的 ADR 仍逐份列在表上。只是歡迎頁、不列 ADR 的 `index.md`（例如 log4brains 產生的）不算索引。

理由是版控：ADR 多半進版控、團隊共享，改動有 review；筆記多半只在本機。兩邊說法衝突時，團隊看得到的那份才是共識。

所以沒進版控的 ADR 不適用這條。ADR 表上標「（未進版控）」的那幾份只在本機，份量跟筆記一樣，跟筆記衝突時不自動照它做，先問使用者。直接看目錄時，用 `git ls-files <ADR 路徑>` 確認，沒有輸出就是還沒進版控；專案本身不是 git repo 時，整個 ADR 目錄都當成未進版控。

### 寫：任務收尾

三步，缺一不可：

```bash
bash <SCRIPTS>/wn-new.sh "這次做了什麼"   # 1. 建檔，回傳路徑
# 2. 把結論寫進那個檔案
bash <SCRIPTS>/wn-reindex.sh              # 3. 重建索引
```

**第 3 步漏掉等於沒寫。** 筆記不在索引上，下次沒有人會找到它。

`wn-new.sh` 不自動重建索引是刻意的——建檔當下內容還是空的，摘要會抓到範本的佔位文字。

#### 檔名與階段序號

`YYYY-MM_NN_主題.md`。`YYYY-MM` 是開工年月（照系統當下，不得為未來），`NN` 是兩位數的**工作階段序號、不是日期**。

同一階段的多份筆記共用一個序號，`wn-new.sh` 預設沿用目前最大序號；開新階段才加 `--new-stage`。接續既有主題的收尾工作沿用原序號。索引依檔名排序，序號決定先後。

用序號不用日期的理由：同階段的多份筆記壓成同一天會把先後關係抹掉，而順序資訊本身有價值。

### 回報：動到哪份檔案就講哪份

讀到筆記內容、或寫入筆記之後，都要在回覆裡列出實際的檔案：

- **讀**：掃了 `docs/working-notes-skill/notes/index.md`，以及命中後實際開的那幾份筆記。沒命中就講「索引裡沒有相關筆記」。
- **寫**：新建或改動的筆記檔，加上索引已重建。

路徑一律用**專案根的相對位置**（例：`docs/working-notes-skill/notes/2026-08_03_主題.md`），不要貼絕對路徑——絕對路徑又長又跟使用者的家目錄綁死，換一台機器就對不上。

理由：使用者要能自己去翻那份檔案、驗證結論是不是真的從那裡來的。只講「根據筆記」而不講是哪一份，等於要對方相信一段查不到出處的話。

#### 第一次建立目錄時

`wn-new.sh`、`wn-plan.sh` 第一次在專案裡寫檔時會建立筆記目錄、佈署 `.gitignore`，stderr 各印一行 `已建立筆記目錄：…`、`已佈署 .gitignore：…`。看到任一行，回覆裡要另外告訴使用者：

- **建了哪個資料夾**：用專案根相對路徑（`docs/working-notes-skill/notes/`），並講出解析到的專案根是哪個資料夾
- **建了 `.gitignore`**：位置在 `docs/working-notes-skill/.gitignore`，筆記與計畫檔預設不進版控；要進版控用 `wn-vcs.sh tracked`

理由：專案裡多出一個使用者沒要求的資料夾，事後才在檔案樹發現，會以為是誤建。專案根找不到標記檔時會退回目前工作目錄，講出專案根，落點錯了當下就看得出來。`.gitignore` 決定筆記會不會被推上遠端，使用者要知道預設是不進版控、以及怎麼改。

## Plan Mode 的計畫檔要留檔

進入 Plan Mode 時與結束 Plan Mode 時，各把該次的計畫 markdown 留存一份：

```bash
bash <SCRIPTS>/wn-plan.sh <計畫檔路徑>
```

留檔路徑是 `<專案根>/docs/working-notes-skill/plans/<標題>.md`。

開始時存的是原始計畫，結束時存的是實際執行後的版本，**同名覆寫**——檔名取自計畫的 H1 標題，兩次自然落在同一個檔案上。

檔名規則與筆記共用：中文字原樣保留，空白與 `/ : ? * " < > | \ ( ) [ ] { }` 及全形括號、引號、`：？！、，。；｜` 一律換成 `-`，連續的 `-` 收成一個。例：`# 範例功能 v2 改版計畫（第二版）` → `plans/範例功能-v2-改版計畫-第二版.md`。計畫沒有 H1 時退回用來源檔名。

計畫檔本身通常在對話工具的暫存區，session 結束就找不到了。留一份在專案裡，之後才查得到「當初是照什麼計畫做的、後來偏離了多少」。

計畫檔與施工筆記的分工：**計畫是動工前的打算，筆記是收工後的結論。** 兩者都留著才看得出中間發生了什麼；不要拿計畫檔充當筆記。

## 寫作規範

**一個任務一份檔案。** 不要追加到既有筆記。

**只留最後結論。** 寫的是「現在長什麼樣、為什麼這樣決定」，不是流水帳——中間試過又放棄的做法、修到一半的數字、待辦清單都不要留。

**第一段要寫清楚「這份在講什麼」。** 那句會被抓進索引，是別人找不找得到它的關鍵。範本已經預留這一行。

**推翻舊結論就回頭改舊筆記。** 後續任務讓某份筆記的結論不成立時，把那份改掉或刪掉該段，別讓過期內容跟新筆記並存。兩份互相矛盾的筆記比沒有筆記更糟。整份被新筆記或規範取代時，用 `wn-obsolete.sh` 標過時，不直接刪：當時的脈絡還留著可查，但不再出現在動工前要掃的主索引。

**寫「為什麼」而不是「改了哪些檔案」。** 檔案清單 git 有，取捨與踩過的坑只有你知道。

### 與規範重複時

專案的規範（`CLAUDE.md`、`AGENTS.md`、專案自己的規範文件）是規則**唯一的完整條文**，筆記只收「為什麼」。兩邊寫同一條規則，改了一邊、漏了另一邊，就會出現兩個版本的規則。

- **筆記與規範重複時，規則放規範**：筆記刪掉重複的條文，換成一句指向規範的哪一節，理由留著
- **刪完沒剩下理由的筆記**（整份都是條文），用 `wn-obsolete.sh` 標過時，「以此為準」寫規範的位置
- 過時標記是筆記 H1 下方第一個非空行的 `> 過時：<以此為準>`，由腳本寫入與拿掉，不要手寫。`wn-reindex.sh` 認得它，會把那份筆記從 `index.md` 移到 `obsolete.md`
- **ADR 也算規範，連理由都歸它**：值得寫 ADR 的決策（難以反悔、沒脈絡會意外、真的有取捨），決策與理由都寫在 ADR，筆記只寫一句「決策見 `docs/adr/0003-xxx.md`」，再補 ADR 不收的東西（踩過的坑、現在的樣子）。專案有 ADR 目錄時，`wn-new.sh` 建檔後會提醒這一條

## 收什麼、不收什麼

施工筆記收的是**這個專案**的結論——這裡為什麼這樣設計、哪個做法在這個 codebase 行不通、動了會壞的地方。

**換到別的專案仍然成立的通則不屬於這裡。** 那種東西寫進專案筆記，等於把它鎖在一個專案裡，下次在別的 repo 遇到同一件事還是要重查。如果你的環境另有跨專案的知識庫機制，通則歸它。

一則結論在專案筆記與跨專案知識庫都成立時：**兩邊各寫一份完整的內容，不要互相連結。** 這裡寫這個專案怎麼落地，那邊寫抽掉專案細節後的通則，該重複的敘述就重複。互引會耦合成一個壞掉的整體——任一邊被改名、搬走或推翻，另一邊就留下一條指不到東西的連結，讀的人只看到「詳見某某」然後沒有下文。各自完整，任一邊單獨讀都成立。

這條只管**跨專案知識庫**，跟上面的「與規範重複時」不衝突：知識庫在專案外，生命週期跟專案無關，所以兩邊各自完整、不互連；本專案的規範與筆記在同一個專案裡一起維護，所以規則只留規範一份，筆記用一句話指向它。

## 版控

預設**不進版控**：`docs/working-notes-skill/.gitignore` 由腳本佈署，筆記與計畫檔只存在本機。

切換走腳本，不要手動編那份 `.gitignore`：

```bash
bash <SCRIPTS>/wn-vcs.sh              # 印出目前狀態
bash <SCRIPTS>/wn-vcs.sh tracked      # 筆記進版控（backup-*/ 仍排除）
bash <SCRIPTS>/wn-vcs.sh untracked    # 恢復不進版控
```

`.gitignore` 被手動改過時腳本會拒絕覆寫，要 `--force` 才動。

**切成 tracked 之前先確認筆記內容**：筆記寫的是內部取捨與踩過的坑，進版控就會被推上遠端、被所有能讀該 repo 的人看到。切 untracked 也不會讓已經提交過的紀錄消失，腳本會把移除指令印出來。
